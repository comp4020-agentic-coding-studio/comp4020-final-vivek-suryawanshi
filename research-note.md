# Agent autonomy should depend on how well we can check the work

Coding agents can produce changes faster than a person can carefully review them. This creates a difficult question: should developers reduce agent autonomy to preserve control, or change how they check software? My position is that autonomy should increase only where teams can produce reliable evidence that a change meets its requirements. People should remain responsible for choosing those requirements and understanding the system well enough to challenge the evidence. Good practice therefore depends on the relationship between autonomy, verification and understanding, rather than the amount of code generated.

Barke, James and Polikarpova’s Grounded Copilot helps explain why one level of supervision cannot suit every task. Their study observed 20 participants and distinguished acceleration, where programmers know what to do next, from exploration, where they use suggestions to discover possible approaches [1]. I read this distinction as a reason to consider the developer’s uncertainty alongside the agent’s capability. A familiar task with clear expected behaviour can support more independent execution. When the developer is still discovering the problem, generating more code can commit the project to assumptions that nobody has examined. However, this qualitative study concerns an earlier programming assistant; it does not establish how safely current agents can complete extended tasks.

Lopopolo’s account of harness engineering at OpenAI presents a strong case for greater autonomy [2]. His team reports building a product with agent-written code by investing in repository knowledge, architectural constraints and feedback tools. This challenges the idea that responsible development requires a human to inspect every line. If agents can run checks, inspect the application and correct failures, compulsory manual review can become a bottleneck. The useful lesson is that autonomy requires engineering around the agent, rather than simply giving it a larger task.

Nevertheless, this is a vendor’s account of one team building a new product. Its estimated development time is not a controlled comparison, and the account acknowledges uncertainty about maintenance over longer periods. I therefore treat it as evidence that extensive autonomy is possible under particular conditions, rather than proof that every team should adopt the same workflow. Its strongest contribution is the description of those conditions.

There is also a limit to what automated checks can establish. Tests compare behaviour against expectations, but somebody must decide whether those expectations represent the problem. An agent can implement a mistaken requirement and produce tests that confirm it. Using agents to write tests remains useful, but agreement between implementation and tests is insufficient when both share the same misunderstanding. Acceptance needs evidence connected to something outside that agreement: an independently established requirement, a reproduced failure, or observation of people using the software. My project gave me a small example of this problem. An agent’s redesign plan kept Saturn at 1.3 times Earth’s diameter. Tests based only on preserving that ratio could have confirmed the implementation while missing the scientific error. Checking published diameters exposed the mistaken requirement. This illustrates why verification needs a reference beyond the agent’s own plan.

Naur’s account of programming as theory building explains why this responsibility cannot be reduced to keeping the generated files [3]. He argues that programmers need an understanding of how the program relates to the world, why it takes its particular form, and how it can accommodate change. Documentation supports this understanding but does not replace it. Although his argument predates coding agents, it raises a current question: who can explain and change a system after its generated implementation stops working? I take this as a requirement for accountable understanding of important decisions, rather than a demand to memorise every line.

Willison makes this concern practical through his discussion of cognitive debt [4]. Losing track of how an application’s core works can make later decisions harder. His proposed interactive explanations show that agents can also help developers recover understanding. However, an explanation is another generated output. I would check it against the implementation and observable behaviour before relying on it. His example offers a useful technique, but it does not demonstrate that explanation tools consistently prevent misunderstanding. Read alongside Naur, it suggests that understanding requires active investigation rather than simply requesting a summary.

Taken together, these sources support selective autonomy. Teams can delegate more where requirements are clear, failures are observable and corrections are reversible. Where requirements are uncertain or consequences difficult to undo, they need stronger human investigation and acceptance. The developer’s work increasingly includes designing checks, questioning their coverage and deciding what evidence is sufficient. A successful workflow should make changes easier to justify and maintain, as well as faster to produce. That is the standard by which I would judge good agentic software-development practice.
